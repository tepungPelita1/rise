# PIN Lock Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a server-enforced 4-digit PIN lock to Rise. It has a frosted lock screen, an unlock animation, a remember-device option and a lock switch, and it replaces Cloudflare Access.

**Architecture:** A pure module, `src/lib/server/lock.ts`, does the PIN hashing, signed cookie tokens and lockout escalation. `hooks.server.ts` refuses every non-public path without a valid cookie. The `/unlock` route renders the lock screen and holds the `unlock` and `lock` form actions. The layout hides app chrome on `/unlock` and gets a lock switch.

**Tech Stack:** SvelteKit 3 / Svelte 5 runes, adapter-node, Node 24 `node:crypto` (scrypt, HMAC), and `node:test` with native TS stripping. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-11-20-pin-lock-design.md`

## Global Constraints
- PIN: exactly 4 digits. Lockout: 3 misses → 15 min, then 1 h, then 24 h. A correct PIN resets it.
- Env: `RISE_PIN_HASH` (format `scrypt$<saltHex>$<hashHex>`), `RISE_SECRET` (≥32 hex chars). They are never committed.
- Cookie `rise_unlock`, value `v1.<issuedAtMs>.<hmacHex>`, httpOnly, SameSite=Lax, path `/`, Secure on https. Remember = maxAge 400 days, otherwise a session cookie.
- Public paths when locked: `/unlock`, `/api/health`, `/_app/*`, `/favicon.svg`, `/manifest.webmanifest`, `/apple-touch-icon.png`, `/icon-*`.
- Copy: "Enter PIN to see progress, tepungPelita".
- Production without `RISE_PIN_HASH` → locked, and the screen says "PIN not set up". Dev without a hash → unlocked.

## Review Focus
- A tampered or garbage cookie (`v1.abc.def`, an empty one, a wrong signature) must count as locked. Tested in Task 1.
- A POST form action sent while locked must get 401/redirect and must never mutate data. Tested in Task 2 (curl).
- The layout load on `/unlock` must not leak `inboxCount`. Tested in Task 2 (curl of the `/unlock` HTML).
- Non-digit or wrong-length input (`"12a4"`, `"12345"`) is rejected and does **not** count as a miss. Tested in Task 1.
- A cookie from an old secret (after a PIN change) is invalid. Tested in Task 1.

### Task 1: lock core (`src/lib/server/lock.ts`)

**Files:** Create `src/lib/server/lock.ts`, `src/lib/server/lock.test.ts`

**Interfaces (Produces):**
- `hashPin(pin: string): string` → `scrypt$salt$hash`
- `verifyPin(pin: string, stored: string): boolean` (timing-safe)
- `isValidPinFormat(pin: string): boolean` (`/^\d{4}$/`)
- `makeToken(secret: string, now?: number): string`; `checkToken(token: string | undefined, secret: string): boolean`
- `createLimiter(): { status(now): { locked: boolean; retryAt: number }; fail(now): void; reset(): void }` with escalation `[15m, 1h, 24h]` (the last value repeats). Every 3 misses starts the next lock.
- `lockConfig(): { enabled: boolean; configured: boolean; hash?: string; secret?: string }`, which reads `process.env` and `dev` from the caller as a parameter: `lockConfig(env, isDev)`

- [ ] Step 1: Write `lock.test.ts` (node:test). Tests: hash→verify true and wrong PIN false; format `"1234"` ✓, `"12a4"` ✗, `"12345"` ✗; token roundtrip ✓; tampered sig ✗, `"v1.abc.def"` ✗, `undefined` ✗; token from secret A fails on secret B; limiter: 2 fails → not locked, 3rd → locked until now+15m; after expiry, 3 more → +1h; then +24h; `reset()` clears; `lockConfig({}, false)` → enabled false; `lockConfig({}, true)`… (dev means disabled) / prod with no hash → enabled true, configured false.
- [ ] Step 2: Run `node --test src/lib/server/lock.test.ts` and expect a FAIL (module missing).
- [ ] Step 3: Implement `lock.ts` with `node:crypto` `scryptSync` (N default, 16-byte salt, 32-byte key), `createHmac('sha256')`, and `timingSafeEqual`.
- [ ] Step 4: Run the tests again and expect a PASS.

### Task 2: server gate (`hooks.server.ts`, `/unlock` route, layout load)

**Files:** Modify `src/hooks.server.ts`, `src/routes/+layout.server.ts`, `src/app.d.ts`. Create `src/routes/unlock/+page.server.ts`.

**Interfaces:** Consumes Task 1. Produces `event.locals.unlocked: boolean`. Actions `?/unlock` (fields `pin`, `remember`) return `fail(400|401|429, { message, retryAt? })` or redirect 303 to `next`/`/`. `?/lock` deletes the cookie and redirects to `/unlock`. The page load returns `{ configured: boolean; retryAt: number | null }`.

- [ ] Step 1: In `handle`, after the CSRF check, compute `locals.unlocked`. If the path is not public and the request is locked: a GET with `accept` text/html → 303 to `/unlock?next=<path>`; anything else → 401. A request to `/unlock` while unlocked → 303 `/`.
- [ ] Step 2: The layout load returns `inboxCount: locals.unlocked ? repo.inboxCount() : 0` and `unlocked`.
- [ ] Step 3: Verify with `RISE_PIN_HASH=$(…) RISE_SECRET=… npm run build && node build`, then curl: `/` → 303; POST `/inbox?/add` → 401; `/api/health` → 200; `/unlock` HTML contains no inbox badge; wrong PIN ×3 → 429; correct PIN → Set-Cookie, and `/` → 200.
